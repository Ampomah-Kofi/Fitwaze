# Deploying the FitWaze field pilot

The repository includes a Render Blueprint (`render.yaml`) that creates the
database and the app, generates the secrets, and serves FitWaze over HTTPS,
which phones need before they will share their location.

## One-time setup (about 10 minutes)

1. Sign in at <https://dashboard.render.com> with your GitHub account.
2. **New → Blueprint**, pick the `Ampomah-Kofi/Fitwaze` repository and the
   branch to deploy (for example `main` once this work is merged).
3. Render shows what it will create: a `fitwaze-db` Postgres database and a
   `fitwaze` web service. Click **Apply**. You are asked for `ORS_API_KEY`:
   leave it empty (it is optional).
4. Wait for the first deploy to finish (a few minutes; it builds the Docker
   image and runs the database migrations). Then open
   `https://fitwaze.onrender.com` (or the name Render assigned) on a phone.

Every push to the deployed branch redeploys automatically.

## Check it before patients use it

On a phone, standing somewhere in Alabama:

1. Create an account, save a profile, do a check-in, tap **Get today's plan**.
2. Tap **Find a route near me** and allow location access.
3. The banner should read *"Routes along real streets and paths near you"*,
   and the lines should follow the streets on the map. Route cards should show
   hill chips (*Flat*, *Gentle hills*, *Hilly*, *N m climb*).
4. Choose a route, tap **Start activity**, walk a little and watch the blue dot.

If routes fail, open the service's **Logs** in Render and look for
`osrm_request_failed` or `elevation_lookup_failed`.

## Put it on the home screen

Once testers open the link, FitWaze can be installed like an app, so it
opens full screen with its own icon and no browser bars:

- **iPhone (Safari):** tap Share, then **Add to Home Screen**.
- **Android (Chrome):** tap **Install** on the card in the app, or use the
  browser menu's **Install app**.

The app shows a card with these steps after sign-in until it is installed.

## What runs where

| Piece | Pilot default | Limits |
| --- | --- | --- |
| App + API | Render web service (`plan: free`) | Free services sleep after 15 minutes idle; the next visit takes ~1 minute to wake. Use the Starter plan (~$7/month) for the pilot so testers never wait. |
| Database | Render Postgres (`plan: free`) | Free databases expire after 30 days. Upgrade to a paid plan (~$7/month) before real pilot data goes in. |
| Street routing | FOSSGIS OSRM servers (`routing.openstreetmap.de`) | Free community service for light use. For the full pilot, self-host on the Alabama map (below). |
| Hills | OpenTopoData `ned10m` (USGS 10 m) | Free public API: 1 request/second, 1,000/day (one request per route search, plus caching). |
| Map background | OpenStreetMap standard tiles | No key; fine for light pilot use under the OSM tile policy. Use a tile provider for a public launch. |

## Moving routing onto your own Alabama map

When the pilot grows, run the routing on the Alabama extract yourself (see
the README, *Alabama: self-hosted map and routing*) on a small VM with ~2 GB
RAM (for example a DigitalOcean or Hetzner droplet), then set
`OSRM_FOOT_URL` and `OSRM_BIKE_URL` in the Render dashboard to that server.
OpenTopoData can be self-hosted the same way with the NED dataset if the
public API's daily limit becomes a constraint.

## Secrets

`JWT_SECRET` and `FIELD_ENCRYPTION_KEY` are generated by Render on first
deploy. **Never change `FIELD_ENCRYPTION_KEY` afterwards**: encrypted health
fields and home locations cannot be read without the key they were written
with. Keep a copy somewhere safe (Render dashboard → Environment).
